# ADR-0002: Polling GitHub API замість Webhooks

- **Статус:** Прийнято
- **Дата:** 2025-04-12
- **Дотичні ADR:** [0004](0004-redis-cache-for-github.md)

## Контекст

Сервіс має дізнаватися про нові релізи у довільному публічному репозиторії, обраному користувачем. Є два принципово різних шляхи:

- **Pull (polling)** — періодично питати `GET /repos/{owner}/{repo}/releases/latest`.
- **Push (webhooks)** — підписатися на події `release` у конкретному репозиторії.

Webhooks GitHub потребують:

1. публічно доступного HTTPS‑ендпоінта на нашій стороні;
2. налаштування webhook **на репозиторії** (адмінські права в цьому репо);
3. валідних секретів (HMAC підпис подій).

Користувачі сервісу — **сторонні люди**, які підписуються на чужі репозиторії; адмінських прав там у нас немає, отже webhooks для довільного repo недоступні.

## Розглянуті варіанти

1. **Polling із спільним інтервалом (`SCANNER_INTERVAL`)** і кешем `latest_release` у Redis.
2. **Webhooks** — лише для self‑hosted сценарію, де користувач сам ставить webhook у свій репозиторій.
3. **Гібрид:** polling за замовчуванням; для своїх репо — webhook як «прискорювач».

## Рішення

Обрано **polling (варіант 1)**.

- Один `time.Ticker` у `ScannerService`, інтервал `SCANNER_INTERVAL` (за замовчуванням 5 хв).
- Опитуються лише репозиторії, на які є **підтверджені** підписки.
- Поверх клієнта GitHub накладено кеш Redis для `RepoExists` і `GetLatestRelease` ([ADR-0004](0004-redis-cache-for-github.md)).
- Стан «що ми вже бачили» зберігається в `repositories.last_seen_tag`; перший виявлений тег стає baseline і **не** триггерить розсилку.

## Наслідки

**Плюси**

- Працює для будь‑якого публічного репозиторію без адмінських прав.
- Просте розгортання: ні reverse‑proxy для webhook, ні менеджменту секретів webhook’ів.
- Контрольоване навантаження на GitHub: число запитів = `count(confirmed_repos) / SCANNER_INTERVAL`, ще зменшене кешем.
- Механізм граничного навантаження — `SCANNER_CYCLE_TIMEOUT`, `SCANNER_REPO_TIMEOUT`, retry/backoff.

**Мінуси / трейдофи**

- **Затримка** виявлення нового релізу — до `SCANNER_INTERVAL + GITHUB_CACHE_TTL` у найгіршому випадку (свідомий компроміс — для нотифікацій про релізи це прийнятно).
- При великій кількості підписок rate‑limit GitHub стане вузьким місцем; потребуватиме токена або ETag/conditional requests.
- На дуже популярні «гарячі» репо все одно витрачаємо запит навіть коли релізів немає.

## Майбутнє

- Додати ETag/`If-None-Match` для отримання `304 Not Modified` без витрат на парсинг.
- Опційно дозволити «pro»‑юзерам підключати webhook на свої репо: інбаунд `/webhooks/github`, перевірка HMAC, запис тегу + миттєвий триггер.
