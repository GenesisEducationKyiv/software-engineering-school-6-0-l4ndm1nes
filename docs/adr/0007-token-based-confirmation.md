# ADR-0007: Confirmation і Unsubscribe через одноразові токени

- **Статус:** Прийнято
- **Дата:** 2025-04-12
- **Дотичні ADR:** [0003](0003-postgres-as-primary-store.md), [0005](0005-smtp-email-delivery.md)

## Контекст

Підписку на email мусить підтвердити **власник скриньки**, а не довільний відвідувач сайту: інакше будь‑хто зможе підписати чужу адресу й створити шум/спам. Аналогічно — відписка має бути виконана однією дією з листа без введення пароля чи логіну.

Класичний патерн — **double opt‑in**: підписка → лист з лінком підтвердження → перехід → запис стає `confirmed`. Розсилка йде тільки `confirmed`‑підписникам.

## Розглянуті варіанти

1. **Одноразові випадкові токени** в URL (`/api/confirm/{token}`, `/api/unsubscribe/{token}`), збережені в БД з унікальними індексами.
2. **JWT** із підписом, без зберігання в БД (stateless). Простіше, але забирає можливість легко інвалідовувати токен (потрібен додатковий «black‑list»).
3. **Сесія + форма** з полем «підтверджую підписку». Зайве для одноразової дії, погіршує UX листа.
4. **Magic link з expiry**, прив’язаний до пристрою/IP. Вищий поріг впровадження за невелику вигоду в нашому домені.

## Рішення

Обрано **варіант 1**:

- При `Subscribe` генеруємо **два** токени `crypto/rand` (32 байти, hex → 64 символи):
  - `confirm_token` — для активації;
  - `unsubscribe_token` — для відписки в кожному наступному листі.
- Обидва зберігаються в `subscriptions` з `UNIQUE` індексами, lookup — за токеном.
- `Confirm(token)`: знаходимо підписку, ставимо `confirmed = TRUE`. Подальші підтвердження тим самим токеном безпечні (idempotent: значення вже `TRUE`).
- `Unsubscribe(token)`: знаходимо підписку, **видаляємо** запис із БД (`DELETE`). Це знімає й можливість повторно використати токен.

## Наслідки

**Плюси**

- Простий, зрозумілий UX для користувача (один клік — і готово).
- Стійкість до brute‑force: 32 байти випадковості, унікальний індекс у БД.
- Працює офлайн: токен у листі довговічний доти, доки рядок є в БД (якщо знадобиться, додамо `expires_at`).
- Не залежить від додаткових сервісів (key‑rotation, JWKS тощо).

**Мінуси / трейдофи**

- Stateful: токен не відкликати «алгоритмічно», тільки видаленням рядка.
- Якщо лист потрапить «не туди» — токен у відкритому каналі. Зменшуємо ризик довжиною токена і рекомендацією HTTPS у проді (HSTS на reverse‑proxy).
- Немає TTL — теоретично можна підтвердити підписку через рік. Якщо стане проблемою — додамо `confirm_expires_at` і фоновий клінер.

## Майбутнє

- `expires_at` для `confirm_token` (наприклад, 7 днів) + фоновий cleanup протермінованих неактивованих підписок.
- Rate‑limit на `/subscribe` за email/IP.
- Опційно — підпис URL HMAC‑секретом для додаткового рівня (token + signature), щоб виявляти «зашумлені» лінки.
