# ADR-0004: Redis як кеш для GitHub API

- **Статус:** Прийнято
- **Дата:** 2025-04-12
- **Дотичні ADR:** [0001](0001-hexagonal-architecture.md), [0002](0002-polling-vs-webhooks.md)

## Контекст

GitHub має жорсткі rate‑limits (60 req/h без токена, 5000 req/h з токеном на користувача). Сканер опитує `GetLatestRelease` для кожного репо з підтвердженою підпискою кожні `SCANNER_INTERVAL`. У більшості тиків відповідь **не змінюється**. Без кешу ми витрачаємо квоту й пропускаємо мережу заради того ж самого тегу.

Окремо — `RepoExists` під час `Subscribe` теж часто повторюється (різні користувачі підписуються на той самий популярний repo).

## Розглянуті варіанти

1. **Жодного кешу.** Просто; але швидко впираємось у rate‑limit і шумимо мережею.
2. **In‑memory LRU всередині процесу.** Простіше за Redis, але втрачається при рестарті, і не масштабується на кілька реплік.
3. **Redis із TTL** через декоратор `CachedClient` поверх `GitHubClient`.
4. **HTTP кешування через ETag/`If-None-Match`.** Реальна оптимізація на боці GitHub (повертає `304`), але потребує зберігати ETag і трохи складніший код. Не суперечить варіанту 3.

## Рішення

Обрано **варіант 3**: Redis‑декоратор поверх HTTP‑клієнта (`internal/adapter/outbound/github/cached_client.go`):

- ключі: `gh:repo_exists:{owner}/{repo}`, `gh:latest_release:{owner}/{repo}`;
- TTL — `GITHUB_CACHE_TTL` (за замовчуванням `10m`);
- значення серіалізуються в JSON (`bool` для `RepoExists`, `domain.Release` для `GetLatestRelease`);
- **`nil`-релізи (404) не кешуються**, щоб не «застрягти» на стані «релізів немає» після того, як вони з’явились;
- помилки Redis не валять сервіс — `logger.Warn` і fallback на прямий HTTP;
- у `main.go` під час старту: якщо `redis.Ping` падає — кеш не вмикається, лог‑warning.

## Наслідки

**Плюси**

- Менше HTTP‑запитів до GitHub: для одного популярного repo за `TTL` робимо 1 запит замість `TTL/SCANNER_INTERVAL`.
- Повторні підписки на той самий repo швидші (`RepoExists` з кешу).
- Кеш — спільний для майбутніх інстансів сервісу.
- Decorator‑pattern зберігає чистоту порту `port.GitHubClient` ([ADR-0001](0001-hexagonal-architecture.md)).

**Мінуси / трейдофи**

- Затримка виявлення нового релізу зростає на час «доживання» застарілого ключа в кеші — у найгіршому випадку **до `SCANNER_INTERVAL + GITHUB_CACHE_TTL`**. Для домену «email‑сповіщення» це прийнятно.
- Redis — додатковий компонент, який треба експлуатувати.
- Між реплікації Redis і кешом тегу можлива race‑умова при «майже одночасних» новій публікації релізу й нашому SET — у нас допустима, бо `last_seen_tag` у БД захищає від подвійних розсилок.

## Майбутнє

- Додати **ETag/`If-None-Match`**: при `304` оновлюємо TTL без перезапису значення, навантаження на GitHub стає мінімальним.
- Адаптивний TTL: коротший для активних репо, довший для архівованих.
