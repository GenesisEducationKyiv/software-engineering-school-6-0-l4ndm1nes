# ADR-0003: PostgreSQL як основне сховище

- **Статус:** Прийнято
- **Дата:** 2025-04-12
- **Дотичні ADR:** [0001](0001-hexagonal-architecture.md), [0007](0007-token-based-confirmation.md)

## Контекст

Потрібно довговічне сховище для:

- довідника репозиторіїв (`owner/repo`, `last_seen_tag`);
- підписок (email + repo, статус підтвердження, токени, таймстампи);
- унікальних обмежень (`UNIQUE(owner, repo)`, `UNIQUE(email, repository_id)`, унікальність токенів);
- транзакційних операцій (наприклад, відкат підписки, якщо лист підтвердження не пішов).

Розглянуті варіанти: PostgreSQL, MySQL, SQLite, NoSQL (Mongo/Dynamo).

## Розглянуті варіанти

1. **PostgreSQL 16.** Реляційна, потужні constraints, чудовий індексинг, `TIMESTAMPTZ`, `ON CONFLICT`, mature‑клієнт `lib/pq`, у більшості хмар є managed‑варіант.
2. **MySQL 8.** Близький за можливостями; менш зручні partial‑indexes; у нас немає причин обирати саме його.
3. **SQLite.** Простіше для dev, але плутанина з конкурентністю та deployment у docker; не підходить під майбутню горизонтальну еволюцію.
4. **NoSQL (наприклад, DynamoDB).** Дорого і незручно для наших унікальних constraints і транзакцій.

## Рішення

Обрано **PostgreSQL 16** із міграціями через `golang-migrate/migrate`.

Структура — дві таблиці `repositories` і `subscriptions` з:

- `UNIQUE(owner, repo)`,
- `UNIQUE(email, repository_id)` — захист від дубль‑підписок,
- `UNIQUE(confirm_token)`, `UNIQUE(unsubscribe_token)`,
- partial‑індексом `WHERE confirmed = TRUE`,
- B‑tree індексами на токени для O(log n) lookup.

Міграції запускаються при старті в `runMigrations(db)` (`cmd/server/main.go`); файли — у `migrations/`.

## Наслідки

**Плюси**

- Багато бізнес‑правил гарантує сама БД (унікальність, FK з `ON DELETE CASCADE`).
- `TIMESTAMPTZ` уникає головного болю з часовими зонами.
- Просто отримати managed‑варіант (RDS у Terraform; локально — `postgres:16-alpine`).
- `lib/pq` — стабільний драйвер, добре сумісний з `database/sql`.

**Мінуси / трейдофи**

- Один SPOF без реплік (для поточного навантаження прийнятно).
- Якщо в майбутньому з’явиться дуже інтенсивний пошук/агрегації — доведеться додавати read‑replica або переходити на CQRS.
- Міграції в `up`‑напрямку на старті: підвищує ризик незапланованої схемотехніки на проді → у майбутньому варто рознести застосунок і міграції (окремий job).
